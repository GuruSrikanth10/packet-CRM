Audit date: 2026-08-16. Branch `enhancement-plan-phases`, HEAD `15daa35`.
Suite at time of audit: **464 passing, 1 failing** (465 collected).

This document is a **successor** to `ENHANCEMENT_PLAN.md`, not a replacement.
That plan's findings F1-F22 and its Phases A-F are implemented and are treated
here as done. This audit re-reads the resulting code and records what is
*still* wrong, what the completed phases left half-wired, and what the system
should build next.

Findings are numbered `G1..G24` so they never collide with `F1..F22`. The
phased plan in section 5 references them by number.

**Headline:** Phases A-F fixed the mechanics. What they did not do is make the
new machinery *reachable*. Three of the six P0 findings below are the same
shape: a Phase D/E/F feature works correctly in isolation but its output never
reaches the place that needs it. The outcome loop cannot see outcomes under

no data. Section 4 is about closing those loops, and it is worth more than any

## 1. P0 -- Correctness

### G1. One transient error permanently stalls offset commits on a partition

`src/utils/kafkaConsumer.py:195`, `230-235`

`_handle_one_message` registers the offset as dispatched *before* the work:

```python
_offset_tracker.dispatched(tp, msg.offset)      # line 195
try:
    ...
    storage = get_casebook_storage()
    if storage.exists(event_id, terminal_only=True):   # can raise
    ...
except Exception:
    logger.exception("Error processing Kafka message", ...)   # line 230
finally:
    if not submitted:
        _queue_semaphore.release()                             # line 234
```

The `except` branch logs and returns. It never calls `_record_completion`, so
the offset stays in `_dispatched` and never enters `_completed`. That is
intentional as far as *this* message goes -- an unprocessed message must not be
committed.

But `OffsetTracker.take_committable` computes a low-water mark:

```python
still_running = self._dispatched[tp] - completed
floor = min(still_running)
committable = {o for o in completed if o < floor}
```

The stranded offset is now permanently the minimum of `still_running`. Every
subsequent offset on that partition is at or above the floor, so
**`committable` is empty forever**. The consumer keeps polling and keeps
processing packets correctly, but stops committing anything on that partition
until the process restarts. On restart the whole backlog since the stall is
redelivered.

Any exception can trigger it: an S3 blip inside `storage.exists`, a
`FileLock` timeout, a `get_casebook_storage()` failure. It is not a rare path.

Second symptom: `_drain_and_commit` loops until `in_flight() == 0`, which can
never become zero, so every shutdown burns the full `SHUTDOWN_DRAIN_SECONDS`.

**Fix.** Distinguish "not done, will be redelivered" from "done, do not commit
but stop blocking". A dispatched offset that will never complete must be
*retired* from `_dispatched` without being added to `_completed`:

```python
def abandoned(self, tp, offset: int):
    """Drop an offset that will never complete, without committing it.

    It stays uncommitted -- Kafka redelivers it, which is correct -- but it
    must not hold the low-water mark hostage for every later offset.
    """
    with self._lock:
        self._dispatched[tp].discard(offset)
```

Call it from the `except` branch of `_handle_one_message` and from
`_process_and_commit`'s failure path. Note the commit floor then advances past
a message that was not processed, so this trades a permanent stall for a
possible loss on that one message: **pair it with a DLQ publish** in the same
branch, exactly as the poison-pill path already does, so nothing is dropped
silently.

**Test:** dispatch offsets 10, 11, 12; make 11 raise; assert 10 and 12 commit
and that a DLQ message was published for 11.

### G2. The outcome loop does not work under the S3 storage backend

`src/utils/outcomes.py:60-63`, `111-123`

Phase D built the outcome loop against the filesystem. Phase F added
`S3CasebookStorage`. Nothing reconciled them.

```python
directory = casebook_dir(event_id)                 # LOCAL_CASESHEETS_DIR
casebook_file = directory / "casebook.json"
if not casebook_file.exists():
    raise UnknownEventError(...)                   # line 63
```

`outcomes.py` never calls `get_casebook_storage()`. With
`CASEBOOK_STORAGE_BACKEND=s3`, no `casebook.json` is ever written locally, so:

- `POST /outcome/{event_id}` returns **404 for every event**, always.
- `record_outcome.py --list-pending` reports nothing pending, always.
- `iter_outcomes()` walks `LOCAL_CASESHEETS_DIR`, which is empty, so
  `accuracy_report` prints "No outcomes recorded yet" regardless of history.

The consequence is worse than a broken endpoint. `ENHANCEMENT_PLAN.md` section 4.1
calls the outcome loop "the single biggest gap" and makes every Phase E
decision -- confidence calibration, runbook promotion, regression detection --
depend on it. Under the very backend Phase F introduced to enable scale-out,
that loop silently produces an empty dataset. An operator would read
"0 outcomes" as "nobody has recorded verdicts yet" rather than "this cannot
record verdicts."

Even on the local backend it is fragile: outcomes are written to
`local_casesheets/`, which `.gitignore` excludes and `prune_casesheets.py`
deletes wholesale (`shutil.rmtree(directory)`) once a casebook passes
`--older-than-days`. The accuracy history is destroyed by routine hygiene.

**Fix.** Route outcome read/write through `CasebookStorage`:

- `record_outcome` uses `storage.load(event_id, "casebook.json")` for the
  existence check and `storage.save(event_id, outcome, filename="outcome.json")`
  for the write.
- Add `list_events()` to the `CasebookStorage` protocol (local: `iterdir`;
  S3: `list_objects_v2` paginated on the prefix) and build `iter_outcomes()`
  on it.
- Exclude `outcome.json` from `prune_casesheets.py`'s deletion set, or move
  outcomes to their own prefix entirely.

### G3. Log artifacts bypass the storage abstraction

`src/log_pipeline/pipeline.py:265-283`, `src/log_pipeline/snapshot.py:45-51`

The same defect as G2, one layer down. `_write_artifact` and
`snapshot.save` write straight to `casebook_dir(event_id)` on local disk:

| Artifact | Written by | Storage backend respected |
|---|---|---|
| `casebook.json` / `status.json` | `CasebookStorage` | yes |
| `raw_logs.txt` | `pipeline._write_artifact` | **no** |
| `reduced_logs.txt` | `pipeline._write_artifact` | **no** |
| `raw_logs_k8s.jsonl` + meta | `snapshot.save` | **no** |
| `outcome.json` | `outcomes.record_outcome` | **no** (G2) |

`ENHANCEMENT_PLAN.md` F22 named this exactly -- "the log pipeline writes to the
local filesystem even when `CASEBOOK_STORAGE_BACKEND=s3`, because it bypasses
the storage abstraction entirely" -- and the Phase D commit fixed only the
*path duplication* half, leaving the storage-bypass half.

Under S3 with more than one replica the practical effects are:

- The casebook's `rejection_logs` field points at an S3 URL (via
  `upload_logs_to_s3`) but the on-disk trace referenced in
  `_format_error_path`'s "saved at {log_file_path}" line lives on whichever
  pod happened to run the packet, and dies with it.
- **Snapshot reuse silently stops working.** `snapshot.load` is the mechanism
  that makes the Kubernetes source viable at all (see `snapshot.py`'s module
  docstring: retries, DLQ replays, and checkpoint resumes all depend on it).
  A retry landing on a different pod finds no snapshot and re-hits the
  cluster, or gets nothing because the kubelet has since rotated the window.
  Nothing reports this; the fetch just returns fewer records.

**Fix.** Add a blob seam beside the JSON one --
`storage.save_artifact(event_id, filename, bytes)` /
`load_artifact(event_id, filename)` -- implemented for both backends, and point
`pipeline._write_artifact`, `snapshot.save/load`, and `outcomes` at it. The
local implementation is what exists today, so this is additive.

### G4. `/ready` builds a new checkpointer on every probe

`src/api/routes.py:242`, `247-251`; `src/core/checkpointer.py:69`

```python
if backend == "postgres":
    get_checkpointer()      # builds a NEW PostgresSaver, connects, runs setup()
    db_ready = True
else:
    conn = sqlite3.connect(str(CHECKPOINT_DB_PATH))
    conn.execute("SELECT 1")
    conn.close()
```

`get_checkpointer()` is not memoised. `get_agent()` calls it once and caches
the compiled graph, so nothing surfaced this -- but `/ready` calls it directly.
Each call opens a Postgres connection, runs `setup()` (a DDL round-trip), and
returns a saver that is **never closed**; `from_conn_string(...).__enter__()`
has no matching `__exit__`.

An orchestrator probing `/ready` every 5 seconds opens 12 connections a
minute, none released. Postgres `max_connections` is exhausted in under an
hour, which takes down not just the probe but every replica sharing that
database -- i.e. the readiness probe becomes the outage. The SQLite path leaks
file handles more slowly but on the same curve.

**Fix.** Memoise `get_checkpointer()` behind a module-level singleton and a
lock, mirroring `get_agent()`. Then `/ready` should not call it at all -- give
`checkpointer.py` a cheap `health_check()` that runs `SELECT 1` on the
*existing* connection.

### G5. `routes.py` re-parses synthesis with its own regex and discards `confidence`

`src/api/routes.py:440-452`, `501-532`

Phase E introduced `src/models/synthesis.py` with `parse_synthesis`,
`SynthesisResult`, and `apply_confidence_policy`, and wired them into
`synthesis_node`. `routes.py` was never updated. It still runs the original
three-tier regex fallback on the same string the orchestrator already
validated and serialised:

```python
fenced_match = re.search(r"```(?:json)?\s*([\{\[].*?[\}\]])\s*```", ...)
...
except Exception:
    investigation_result = final_message
...
if not isinstance(investigation_result, dict):
    investigation_result = {"rejection_description": str(investigation_result)}
```

Two consequences.

**The `action: null` path that section 4.3 set out to eliminate is still live.** The
orchestrator guarantees a valid `SynthesisResult`, but the escalation strings
it emits on the unrepairable path are plain dicts, and any future node that
returns raw text lands in this fallback and produces a casebook with
`action: null` -- indistinguishable downstream from a packet the agents
genuinely could not classify, which is the exact failure section 4.3 describes.

**`confidence` is computed and then thrown away.** `apply_confidence_policy`
caps confidence against evidence gaps and can abstain on it;
`model_dump_json()` serialises it. Then `casebook_data["resolution"]` is built
from four hand-picked keys:

```python
"resolution": {
    "source": ..., "synthesis": ..., "action": ..., "resident_action": ...
}
```

No `confidence`. It never reaches the casebook, so it never reaches
`record_outcome`'s denormalised fields, so `accuracy_report` cannot correlate
confidence against correctness. `synthesis.confidence_threshold()`'s docstring
says the threshold must stay at 0 until "`accuracy_report` shows what a given
confidence is worth" -- and with confidence unpersisted, it never can. The
abstention feature is permanently ungateable by construction.

**Fix.** Delete the regex block; call `parse_synthesis(final_message)`. On
`None`, write an explicit `FAILED_SYNTHESIS_PARSE` terminal status rather than
a null-action casebook. Persist `confidence` and an `abstained` boolean into
`resolution`, and denormalise both in `outcomes.record_outcome`.

## 2. P1 -- Reliability and scale-out

### G7. No consumer-group rebalance handling

`src/utils/kafkaConsumer.py:45-105`, `324-365`

`OffsetTracker` keys everything on `TopicPartition` and holds those entries
for the process lifetime. `KafkaConsumer` is constructed with no
`ConsumerRebalanceListener`.

When the group rebalances -- a second consumer starts, one is restarted, a
`max_poll_interval_ms` expiry evicts a member -- partitions are reassigned.
This consumer keeps stale `_dispatched` / `_completed` entries for partitions
it no longer owns, and `_commit_ready_offsets` will happily
`consumer.commit()` them. Best case that raises `CommitFailedError`, which is
swallowed at line 245 and logged. Worse case it commits an offset for a
partition now owned by a different member, moving that member's committed
position and skipping messages it is still working on.

`ENHANCEMENT_PLAN.md` Phase F's exit criteria are literally "two API replicas
**and two consumers**, one topic". Running two consumers is the condition that
makes rebalance certain, and section 7.4 records that this validation was never run --
so this has never been exercised.

**Fix.** Pass a `ConsumerRebalanceListener` to `consumer.subscribe()`. On
`on_partitions_revoked`: commit what is safe for the revoked partitions, then
drop their tracker entries. On `on_partitions_assigned`: assert the tracker
has no stale state for them. Add a test driving revoke/assign against a fake
consumer.

### G8. `/health` cannot see the consumer in any multi-pod deployment

`src/api/routes.py:206`

```python
heartbeat_file = Path(__file__).resolve().parent.parent.parent \
    / "local_checkpoints" / "consumer_heartbeat.txt"
```

The API reads the consumer's heartbeat off the local filesystem. That works
under `start.py`, where both run on one host. It cannot work when the API and
the consumer are separate pods -- which is the deployment Phase F exists to
enable -- so `consumer_alive` is permanently `false` and
`last_heartbeat` permanently `null`.

If anything alerts on `consumer_alive`, it fires forever and gets muted. F9
went to real trouble to stop a starving heartbeat from killing healthy pods;
this quietly reintroduces a heartbeat nobody can read.

**Fix.** The heartbeat is a liveness signal for the *consumer* process, so
serve it from the consumer: give `main_consumer.py` a tiny HTTP listener with
its own `/health`, and let the consumer's own liveness probe hit that. The
API's `/health` should then report only what the API itself knows -- process
up, executor saturation, checkpoint reachability -- and drop `consumer_alive`
rather than reporting a value it cannot obtain.

### G9. The API has no graceful shutdown

`src/main_api.py:13-15`, `src/api/routes.py:46-48`

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
```

F12 gave the consumer signal handlers, a bounded drain, and a final commit.
The API got none of it. `_agent_invoke_executor` is a module-level
`ThreadPoolExecutor` whose threads are non-daemon and which is never shut
down. On SIGTERM, uvicorn stops accepting connections, but in-flight
`agent.invoke()` calls keep running and the process lingers until the
orchestrator's `terminationGracePeriodSeconds` expires and SIGKILL lands
mid-investigation.

Every one of those packets leaves an `IN_PROGRESS` `status.json` behind, which
blocks reprocessing for `MAX_IN_PROGRESS_AGE_SECONDS` -- 30 minutes by
default. That is precisely the failure F12 fixed on the consumer side. A
rolling deploy of the API stalls every in-flight packet for half an hour.

**Fix.** Use the `lifespan` shutdown half: flip a "draining" flag so `/ready`
starts returning 503 (the orchestrator stops routing new work), wait up to a
bounded budget for the executor to finish, then
`_agent_invoke_executor.shutdown(wait=False, cancel_futures=True)`. For
whatever is still running at the deadline, write `FAILED_SHUTDOWN` via
`save_terminal` so no `IN_PROGRESS` stub is left.

### G10. `es_breaker` guards the whole source chain, including Kubernetes

`src/tools/tool_registry.py:345`

```python
@es_breaker
@retry_transient
def fetch_logs_for(event_id, extra_identifiers=()):
    return reduce_logs(event_id, extra_identifiers=extra_identifiers)
```

`reduce_logs` runs `source_chain.fetch_with_fallback`, which may serve
Kubernetes, Elasticsearch, or both. So a breaker named and reasoned about as
the Elasticsearch breaker counts failures from every source and, once open,
fails fast for every source.

Two concrete effects:

- A Kubernetes-only deployment (`LOG_SOURCE=kubernetes`) has its fetches
  gated by `es_breaker`. `k8s_breaker` already wraps `KubernetesLogSource.fetch`
  (added by F8), so Kubernetes failures are counted twice, against two
  breakers, one of which has nothing to do with Kubernetes.
- With the default `LOG_SOURCE=kubernetes,elastic`, a Kubernetes outage that
  the chain correctly falls back from can still trip `es_breaker` -- and then
  the *Elasticsearch* fallback is refused, even though Elasticsearch is
  healthy. The fallback chain is disabled by the failure it was built to
  absorb.

**Fix.** Move the breaker to where the failure is attributable. Each source
owns its own breaker (`k8s_breaker` already does; add one inside
`ElasticLogSource.fetch`), and `fetch_logs_for` carries none. `chain.py`'s
comment about preserving `@es_breaker` semantics needs updating in the same
change.

### G11. A cached rule is unreachable while the DB breaker is open

`src/tools/tool_registry.py:187-213`

```python
@db_breaker
@retry_transient
def _lookup_rule_json(reason_code: str) -> str:
    with _rule_cache_lock:
        cached_result = _rule_cache.get(reason_code)     # inside the breaker
```

The cache lookup sits inside the circuit breaker. When `db_breaker` opens
after three failures, `pybreaker` raises `CircuitBreakerError` before the
function body runs, so even a reason code whose rule is already in the TTL
cache fails.

`investigator_node` catches it and substitutes prompt text:

```python
db_rule = f"Rule lookup failed for reason code {reason_code}: {e}"
```

So during a 60-second MySQL blip, every packet gets a degraded Investigator
prompt with no rule configuration -- including the high-volume reason codes
whose rules are sitting in memory, valid and unexpired. The cache was
explicitly added (1.1) so a transient blip would not poison a reason code; the
breaker placement undoes that.

**Fix.** Check the cache first, outside the breaker; only the miss path enters
it.

```python
def _lookup_rule_json(reason_code):
    with _rule_cache_lock:
        cached = _rule_cache.get(reason_code)
    if cached is not None:
        return cached
    return _lookup_rule_uncached(reason_code)   # @db_breaker @retry_transient here
```

### G12. The retry prompt drops the evidence the Reviewer asked for

`src/core/agent_orchestrator.py:304-313`

```python
if is_retry:
    prompt = (
        f"Your previous analysis:\n{investigation}\n\n"
        f"Reviewer Feedback (You MUST fix your previous analysis): {feedback}\n\n"
    )
```

The 2.3 token optimisation sends only the delta on retry: prior investigation
plus feedback. The payload, the **logs**, and the DB rule are all omitted, on
the reasoning that they were sent on attempt one and have not changed.

That reasoning holds for the payload and the rule. It does not hold for the
logs, because the Reviewer's most common rejection is precisely that the
findings are not grounded in the log evidence -- `ReviewerAgent.md` exists to
enforce citation. The Investigator is then asked to fix a citation problem
with the logs removed from its context. It cannot comply. It produces another
ungrounded analysis, the Reviewer rejects again, and the loop runs to
`MAX_INVESTIGATION_RETRIES` and escalates.

The optimisation saves one log payload per retry and can cost three full
LLM round-trips plus a manual review. On any packet that retries at all it is
plausibly a net loss.

This is now measurable: `metrics.INVESTIGATOR_RETRIES` records the
distribution, and G18's outcome data would show the escalation rate.

**Fix.** Keep the logs on retry; drop only the payload projection and the rule
text (both genuinely static and both already reflected in the prior
investigation). Then measure `packetcrm_investigator_retries` before and
after, and let the histogram decide.

| **`FAILED_TIMEOUT`** | 419 | **no** |
| **DLQ (unhandled exception)** | 435 | **no** |
| late-result discarded | 547 | no |
| success | 568 | yes |

`packetcrm_packets_total{status=...}` therefore has a `status` label that can
only ever take success values, and the timeout and DLQ rates -- the two numbers
you would page on -- are structurally unobservable. Likewise `PACKET_DURATION`
excludes every slow packet that timed out, which biases p95 latency downward
by dropping exactly the tail it measures.

**Fix.** Record both metrics in a `finally`, or via a small context manager
entered right after `packet_started_at` is set, with the status resolved at
exit.

### G16. `RUNBOOK_LOOKUPS` records only hits

`src/core/agent_orchestrator.py:176` is the sole call site, and it is
`outcome="hit"`. The metric's own help text promises "hit, miss,
fingerprint_mismatch, error".

A counter with no denominator cannot express a rate. Runbook hit rate is named
in `ENHANCEMENT_PLAN.md` section 4.5 as one of the seven things that were unknowable,
and it still is. It is also the primary input to the section 4.2 rollout decision.

**Fix.** Increment `outcome="miss"` at both early `return {"resolution_source":
"agent"}` branches, `outcome="fingerprint_mismatch"` at the fingerprint check,
`outcome="error"` in the `except`, and `outcome="shadow"` on the shadow path.

### G17. `LLM_CALLS` has no error outcome

All six call sites record success-ish outcomes (`ok`, `invalid`,
`unrepairable`, `abstained`). A call that raises propagates through
`@retry_transient` and `@llm_breaker` and is counted nowhere, so LLM error
rate and breaker-trip frequency are unmeasurable -- the latter also named in
section 4.5 as an unknowable.

**Fix.** Wrap each `invoke_*` in try/except, increment
`outcome="error"`, re-raise. Add a `BREAKER_STATE` gauge sampled from
`pybreaker`'s `current_state`.

### G18. The shadow-runbook comparison never leaves the log stream

`src/core/agent_orchestrator.py:492-507`

Shadow mode computes the runbook's proposed resolution, runs the agents
anyway, compares the two, and logs a `"Shadow divergence"` warning on
disagreement. Then `shadow_runbook_resolution` is dropped: it is not in
`GraphState`'s return from `synthesis_node`, not in `casebook_data`, not in
`outcome.json`.

`outcomes.summarise` groups by `resolution_source`, which for a shadowed
packet is `"agent"`. So `accuracy_report`'s agent-vs-runbook comparison -- the
one described in `accuracy_report.py`'s own docstring as "the runbook
promotion gate" -- can only compare runbooks that are **already being served**
against agents. And a runbook cannot be cleared to serve until it has been
compared.

That is a closed loop with no entry point. section 4.2's stated sequence is "run
`RUNBOOK_MODE=shadow` in production for a sample period, use section 4.1's accuracy
data to confirm the runbook and the agents agree, then flip to `serve`". Step
two is not implementable as built. The only shadow evidence is unstructured
warning lines, which no aggregation exists for.

**Fix.** Persist the shadow result into the casebook:

```python
"resolution": {
    ...,
    "shadow": {
        "runbook_id": ..., "action": ..., "resident_action": ...,
        "agreed": bool,
    },
}
```

Denormalise `shadow_action` and `shadow_agreed` in `record_outcome`, and add a
`--shadow` mode to `accuracy_report` that reports, per reason code: how often
the shadow runbook agreed with the agents, and -- using the operator verdict --
what the runbook's accuracy *would have been*. Add a
`packetcrm_shadow_divergence_total{runbook_id}` counter.

That report is the promotion gate. Once it exists, `RUNBOOK_SERVE_ALLOWLIST`
can be populated from evidence instead of intuition.

## 4. P2 -- Security, supply chain, hygiene

### G19. The learning-rule loop is an indirect prompt-injection path

`src/core/agent_orchestrator.py:210-229`, `src/tools/promote_rules.py:59-71`

The chain is:

1. Log lines are fetched into the Investigator's context. Log content is
   influenced by upstream request data.
2. The Reviewer may call `add_learning_rule(rule_text, reasoning)`, whose
   arguments are LLM-generated text derived from that context.
3. The proposal is appended to `prompts/pending_rules.jsonl`.
4. `promote_rules.py` appends it **verbatim** into `InvestigatorAgent.md` and
   git-commits it:

```python
f_target.write(f"\n- CRITICAL RULE: {entry.get('proposed_rule')}\n")
```

`InvestigatorAgent.md` is the system prompt for every subsequent packet. So a
crafted string in a log line can, if it survives one interactive `y/N`,
permanently modify the system prompt of every future investigation -- labelled
"CRITICAL RULE" to maximise its weight.

The only control is a human pressing `y` on a single line of text with no
diff, no length limit, and no content validation. `validate_generic_text`
already exists for runbook drafts and is not applied here.

Severity is moderated by the human gate and by the fact that log content is
not directly attacker-authored in most flows. It is raised by the UIDAI
context, by the persistence and privilege of the target, and by the fact that
the promotion is auto-committed to git, which makes it look reviewed.

**Fix.** Apply `validate_generic_text` to `proposed_rule` at write time in
`add_learning_rule`; cap length (a rule is a sentence, not a paragraph);
reject rules containing instruction-shaped strings ("ignore", "disregard
previous", "system:", fenced blocks); show a full diff in `promote_rules.py`
and require typing the reason code rather than `y`; drop `check=True` on the
auto-commit so promotion and commit are separate operator decisions.

### G20. `queue_for_replay` forwards resident contact details chosen by the LLM

`src/tools/tool_registry.py:388-422`

`notificationEmail` and `notificationMobile` are tool arguments -- the LLM
supplies them -- and are POSTed to `OIS_FEIGN_BASE_URL` when
`ENABLE_AUTO_REPLAY=true`. Nothing validates that they belong to the packet in
question. A hallucinated or log-scraped address would be sent a real
notification about someone else's enrolment.

1.8 already moved these out of query params so they would not land in access
logs, which shows the sensitivity was understood; the provenance was not
addressed.

**Fix.** Do not let the model choose these. Populate them server-side from the
validated payload, and have the tool accept only `id`, `idType`, `priority`,
and `category`. If they are genuinely not in the payload, send neither and let
OIS resolve them from the `id`.

### G21. Dependencies are half-pinned and CI runs a different Python than development

`requirements.txt` pins 11 packages exactly and leaves 15 floating, including
`langgraph`, `kubernetes`, `elasticsearch`, `SQLAlchemy`, `PyMySQL`,
`structlog`, `drain3`, `cachetools`, `pybreaker`, `tenacity`, and `pytest`.

`langchain-core==1.3.1` is pinned but `langgraph` is not -- and F2, the single
most damaging bug in the previous audit, was caused by a langchain-core
behaviour change (`@tool` producing a non-callable `StructuredTool`). The
adjacent package that most closely tracks it is unpinned.

Separately, `.github/workflows/test.yml` sets `python-version: "3.12"` while
`pyrightconfig.json` points at `.venv/lib/python3.14/site-packages` and the
codebase runs 3.14 locally. A green CI run does not demonstrate the code works
on the interpreter it is developed and deployed on.

**Fix.** Pin everything, generate a `requirements.lock` with hashes, add
Dependabot or Renovate, and align CI to 3.14 (or run a matrix of both).

### G22. Test and quality gaps

**a. No end-to-end test.** All 465 tests are unit tests over mocks. There is
no test that drives `POST /process-rejection` with a stubbed LLM and asserts
the resulting casebook shape. That is exactly the test that would have caught
F2, where `runbook_lookup_node` raised `TypeError` and sent every
runbook-matching packet to the DLQ -- every unit test passed while the system
was end-to-end broken.

**b. No pytest configuration.** No `pytest.ini` / `pyproject.toml`, so no
`testpaths`, no markers, no coverage floor. `test_payload.py` sits at the
repository root, matches pytest's `test_*.py` discovery pattern, and executes
network-free but side-effecting code at import. CI happens to dodge it by
running `pytest tests/`; a bare `pytest` does not.

**c. CI runs no lint or type check.** `pyrightconfig.json` exists and is never
executed by anything. There is no ruff/flake8 step. The `print()`-vs-structlog
inconsistency this audit just cleaned up would have been caught by a lint rule
and will drift back without one.

**d. `.env.example` ships a personal path.** Line 17:
`MOCK_DB_PATH=C:\Users\guru.nisg\Downloads\cre_rules.csv`. Flagged as minor in
the previous audit; still present.

### G23. Prompt changes are unattributable

Prompts are plain files with no version identifier, and the casebook records
no prompt version. After Phase D there is an accuracy figure per reason code --
but when it moves, there is no way to tell whether a prompt edit, a model
change, a rule change, or a traffic-mix change caused it.

The rule side of this is already solved: `rule_fingerprint` pins a runbook to
the rule it was derived from. The prompt side has no equivalent.

**Fix.** Hash the four prompt files plus `agent_policy_context.md` at graph
construction, expose it as `prompt_fingerprint`, write it into
`resolution.provenance`, and denormalise it in `record_outcome`. Then
`accuracy_report --by-prompt` becomes a regression detector.

### G24. Agent construction is more expensive than the work requires

Three smaller efficiency items in `agent_orchestrator.py`:

- **`create_react_agent` with no tools** (lines 201, 202). The Investigator and
  LogFilter agents are built with `tools=[]`. A ReAct agent with no tools adds
  the agent loop and tool-calling schema to what is a single-turn completion.
  A direct `llm.invoke([...])` is equivalent and cheaper in both tokens and
  latency.
- **LogFilter runs on the `complex` tier** (line 202). Stripping lines that do
  not belong to a target event ID is mechanical extraction -- the archetypal
  `simple`-tier task, and it runs on every packet when
  `ENABLE_LOG_FILTER_AGENT=true`.
- **`agent_policy_context.md` is appended to every prompt** (`load_prompt`,
  lines 87-92), including LogFilter's, which has no use for business policy.
  That is the full policy document in the context window of every filter call.

None of these is a bug. Together they are a straightforward cost reduction on
a system whose cost is dominated by LLM calls.

## 5. New implementation opportunities

Ordered by leverage. Each is scoped in the phased plan below.

**N1. Close the shadow-to-serve loop (G18 + G16).** The single highest-value
item. Once shadow results are persisted and reportable, runbook rollout becomes
evidence-driven, and runbook-served packets are the cheapest and fastest
resolutions the system can produce. Everything else in section 4.2 of the previous
plan is gated on this.

**N2. Confidence calibration (G5 + G23).** Persist `confidence`, then produce a
reliability curve from recorded outcomes: bucket packets by confidence, plot
observed accuracy per bucket. That is what tells you where
`SYNTHESIS_CONFIDENCE_THRESHOLD` should sit. Until then the abstention feature
is code that cannot be turned on responsibly.

**N3. A storage-backed artifact layer (G2 + G3).** One seam
(`save_artifact`/`load_artifact`/`list_events`) fixes the outcome loop, log
artifacts, and snapshot reuse under S3, and unblocks the multi-replica
validation that section 7.4 records as never run.

**N4. An end-to-end contract test (G22a).** A stub LLM returning canned
synthesis JSON, driven through `POST /process-rejection`, asserting the
casebook. Add cases for: runbook hit, shadow divergence, synthesis repair,
unrepairable escalation, timeout, DLQ. This is the regression net the previous
audit's failures went through.

**N5. An SLO and alerting pack.** Metrics exist; nothing consumes them. Ship
Prometheus recording rules and alerts for packet error rate, p95 latency, DLQ
rate, breaker state, runbook hit rate, and evidence-gap rate, plus a Grafana
dashboard JSON. Cheap, and it converts Phase D from instrumentation into
operations.

**N6. Per-packet cost accounting.** `LLM_TOKENS` is collected by node. Add a
price table per model tier and expose cost per packet and per reason code.
That number is what justifies the runbook rollout, the tier assignments in
G6/G24, and the retry-loop tuning in G12 -- in the terms a budget owner uses.

**N7. DLQ replay tooling.** Packets reach the DLQ from four paths and there is
no tool to inspect, filter, or replay from it. `approve_replays.py` handles the
OIS replay queue, which is a different thing. An operator facing a DLQ backlog
after an outage currently has no supported path back.
